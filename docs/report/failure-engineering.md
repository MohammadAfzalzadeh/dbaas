# Failure engineering

## Method and safety boundary

Each live experiment ran against an owned disposable kind cluster. Worker termination and eviction are different experiments. Clients run outside the failed worker, record commit acknowledgements, and verify the acknowledged ID set afterward. Failed transactions can have uncertain outcomes; the harness does not silently replay them. Baseline, disruption, recovery and cleanup artifacts are retained.

Phase 6 adds no live experiments. Its role is to reconcile the existing results, including contradictory outcomes. [Authoritative classifications](../evidence/README.md) and [measurement definitions](performance-results.md).

## The unresolved replica recovery anomaly

**Initial result: FAILED. Final classification: UNRESOLVED HISTORICAL FAILURE + NOT REPRODUCED IN SUBSEQUENT CLEAN RUNS.**

The first abrupt-loss experiment elected a new primary, but a survivor requested WAL position `0/14000000` on timeline 4 while the primary flush position was `0/130799C8`. It remained in archive recovery beyond the original bound and required manual Patroni reinitialization. This is an observation, not an established causal chain. The exact transition that produced the incompatible recovery state is unknown. [historical evidence](../../results/runtime/multinode/dbaas-phase5-8a3ad9f385/replica-recovery-diagnostic.json)

Three later clean runs recovered automatically without reinitialization. Their changed workload and clean starting state limit comparison. They establish successful recovery in those runs; they do not explain the earlier failure. Calling the defect fixed would require a reproducer or a defensible cause-and-regression chain. [evidence](../../results/runtime/multinode/dbaas-phase5-bc4cacdf48/failover-windows.json)

## Interpreting success

A primary accepting SQL does not imply every replica or client has recovered. A retained acknowledged-ID set does not prove zero RPO under asynchronous replication. A backup Job finishing does not prove every restore target has a complete WAL chain. A live alert firing does not prove notification delivery.

The strongest evidence combines independent observations: SQL role/data checks, Patroni membership, endpoint state, object-store keys, client acknowledgements and restored data assertions. [Production gaps](production-gap-analysis.md) define what those observations still do not cover.
